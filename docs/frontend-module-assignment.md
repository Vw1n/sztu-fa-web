# SZTU FA 展示端模块开发分工建议

## 1. 当前项目概况

当前展示端采用 React 19、TypeScript、Vite 和 React Router，首页由协会简介、活动资讯、球队、赛事等区块组成。项目已经具备按领域拆分的 API、类型定义和公共组件，可在不重写首页的前提下继续扩展独立页面。

现有基础能力：

- API：`teams`、`players`、`matches`、`seasons`、`news`
- 公共组件：加载、错误、空状态、分页、赛季选择、区块标题、图片预览等
- 业务模块：球队目录、球队阵容、比赛列表、积分榜、淘汰赛、射手榜、球员生涯
- 路由：已具备基础路由入口，但独立业务页面尚未完整接入

## 2. 推荐人员与模块划分

建议按 5 名开发者分配。人数不足时，可按照优先级合并相邻模块。

| 人员 | 负责模块 | 建议路由 | 优先级 | 主要交付 |
|---|---|---|---|---|
| A | 球队详情 | `/teams/:id` | P0 | 球队资料、赛季阵容、球员入口、相关比赛 |
| B | 比赛详情 | `/matches/:id` | P0 | 比分、比赛状态、事件时间线、阵容、MVP |
| C | 资讯中心 | `/news` | P1 | 资讯列表、分类、分页、公众号链接 |
| D | 球员中心 | `/players/:id` | P1 | 球员资料、生涯数据、赛季表现、所属球队 |
| E | 首页体验与平台基础 | `/` 及全局 | P0 | 路由接入、导航、响应式、SEO、错误页、联调与发布检查 |

### A：球队详情模块

负责范围：

- 新建 `src/pages/TeamDetail/`
- 使用 `fetchTeamById`、`fetchTeamPlayersBySeason`
- 展示队徽、教练、领队、球衣信息等球队资料
- 支持赛季切换和阵容空状态
- 球员卡片预留跳转 `/players/:id`
- 复用 `LoadingSpinner`、`ErrorMessage`、`EmptyState`、`SeasonSelector`

验收标准：直接访问详情 URL 可正确加载；无效 ID 有明确提示；移动端布局可用；刷新页面不丢失状态。

### B：比赛详情模块

负责范围：

- 新建 `src/pages/MatchDetail/`
- 使用 `fetchMatchById`
- 展示主客队、比分、时间、地点、阶段和比赛状态
- 复用现有事件时间线、阵容等组件，避免复制一套实现
- 对未开赛、进行中、已结束三种状态分别展示
- 球队和球员名称预留详情页跳转

验收标准：事件顺序正确；主客队数据不颠倒；缺少阵容或事件时正常降级；无效 ID 有错误状态。

### C：资讯中心模块

负责范围：

- 新建 `src/pages/News/`
- 使用 `fetchNews`
- 实现分页、分类筛选、加载、错误和空状态
- 统一首页活动卡片与资讯列表的数据映射
- 点击资讯时安全打开 `wechatUrl`
- 对缺失封面提供默认图

验收标准：分页和分类切换后数据一致；外链使用安全属性；接口失败时不出现空白页。

### D：球员中心模块

负责范围：

- 新建 `src/pages/PlayerDetail/`
- 使用 `fetchPlayerById`、`fetchPlayerCareer`
- 复用现有 `PlayerCareerCard` 和 `usePlayerCareer` 的业务思路
- 展示球员资料、号码、位置、照片及赛季履历
- 处理无照片、无生涯数据等情况

验收标准：不同赛季的数据归属正确；无数据状态清晰；从球队、比赛模块均可进入球员详情。

### E：首页体验与平台基础

负责范围：

- 在 `App.tsx` 统一接入各业务路由
- 调整 Header，使首页锚点与独立页面导航兼容
- 增加 404 页面和全局错误边界
- 检查桌面端、平板和手机端布局
- 补充页面标题、描述、图片替代文本等基础 SEO 与可访问性
- 负责最终合并、接口联调、构建验证和部署检查

验收标准：所有路由可直接访问和刷新；导航无死链；`npm run lint`、`npm run build` 全部通过。

## 3. 依赖关系与开发顺序

第一阶段可并行开发 A、B、C、D，各负责人只操作自己的页面目录。E 先定义路由和页面导出约定，但暂不频繁改动业务模块。

第二阶段由 E 统一接入路由和导航：

1. 接入球队详情和比赛详情
2. 接入资讯中心和球员中心
3. 首页卡片补充详情跳转
4. 完成响应式、错误页和全链路测试

模块依赖约定：

- A、B 可以链接 D，但不能直接修改 D 的页面实现
- C 可以复用首页 Activities 的视觉样式，但不要直接耦合首页状态
- 只有 E 修改 `App.tsx`、`main.tsx` 和 Header 导航，避免多人产生合并冲突
- API 或类型缺失时先提交接口需求，不在页面目录内自行定义重复领域类型

## 4. 统一开发约定

每个页面目录建议保持一致：

```text
src/pages/ModuleName/
├── ModuleNamePage.tsx
├── ModuleNamePage.css
├── hooks/
├── components/
└── index.ts
```

统一要求：

- 页面通过路由参数获取业务 ID，不依赖上一个页面传入的临时 state
- API 调用集中在 Hook 或现有 API 层，不直接散落在多个展示组件中
- 优先复用 `src/components/common/`
- 不使用 `any`，不复制已有 Team、Player、Match、News 类型
- 每个模块至少覆盖加载、成功、空数据、接口错误四种状态
- 提交前必须执行 `npm run lint` 和 `npm run build`

## 5. 分支与合并建议

建议分支名称：

- `feature/team-detail`
- `feature/match-detail`
- `feature/news-center`
- `feature/player-detail`
- `feature/frontend-integration`

合并顺序建议为 A、B、C、D，最后合并 E 的集成改动。各业务分支不要自行修改路由入口和全局导航；由集成人统一处理，可以显著减少冲突。

## 6. 建议排期

| 阶段 | 时间 | 产出 |
|---|---|---|
| 接口确认与页面骨架 | 0.5 天 | 字段确认、路由和状态设计 |
| 模块并行开发 | 2–3 天 | 四个独立业务页面 |
| 路由接入与联调 | 1 天 | 页面入口、跨模块跳转 |
| 响应式与缺陷修复 | 1 天 | 移动端、异常状态、视觉统一 |
| 验收与发布 | 0.5 天 | lint、build、部署回归 |

整体预计 5–6 个工作日。若只有 3 人，建议优先完成球队详情、比赛详情和平台集成，资讯中心与球员中心放入第二期。

## 7. 暂不建议拆出的工作

- 不建议每人各自创建一套加载、分页或错误组件
- 不建议多人同时调整 Header、App 路由和全局 CSS
- 不建议当前阶段重写 API 层或状态管理方案
- 不建议把管理后台功能混入展示端开发任务

这样划分能让业务页面并行开发，同时把最容易冲突的路由、导航和全局样式集中给一人负责。
